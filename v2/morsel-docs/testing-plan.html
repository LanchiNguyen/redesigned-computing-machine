Usability testing plan

Five moderated sessions, ~40 minutes each, on the v3 prototype (phone-sized browser window or device). Goal: pressure-test the amber assumptions on the wireflow — info scent, trust comprehension, dietary model, and recovery states.

Participants

  • 5 participants, ages 22–35, urban, order out or eat out ≥2× a week, decide from photos (screener: "show me the last food photo that made you order something").
  • Mix: ≥2 who primarily use delivery apps, ≥2 who primarily walk in; ≥1 with a real dietary restriction or allergy (critical for tasks 6, 8, 9).
  • Exclude: food-industry professionals, UX designers.
  • Device: their own phone if possible (mirrors real grip + text size), else provided device.

Moderator script

"Thanks for making time. This is an early prototype of a food-discovery app — some data is fake and some buttons are intentionally limited; none of that reflects on you. I'll ask you to do a few things and think out loud. There are no wrong answers — if something is confusing, that's the app failing, not you. I didn't design it, so be blunt."

  • Warm-up (3 min): "Walk me through how you picked the last place you ate that wasn't routine."
  • Tasks 1–10 below, in order; skip 7–10 if time runs short for a participant, rotating which are skipped across sessions.
  • Wrap (3 min): "If this existed tomorrow, when would you actually open it? What would make you delete it?"

Severity scale

  • S1 — safety/trust breach: user misunderstands the allergy promise or the trust metric in a way that could cause harm or distrust. Fix before any release.
  • S2 — task blocker: cannot complete a core task (choose, save, order handoff) without moderator help.
  • S3 — friction: completes with detours, misclicks, or visible hesitation.
  • S4 — polish: cosmetic or preference-level.

Before / after template

For each S1–S2 finding that changes the design, produce one before/after pair for the case study:

  1. Before: screenshot of the v3 state + one-line finding ("4/5 read 90% as a satisfaction score").
  2. After: screenshot of the revised state + what changed and why it addresses the evidence.
  3. Verdict line: how you'll know it worked (re-test criterion or metric).

Keep pairs at identical crop/zoom so the change reads instantly (template: two phone frames side by side, finding above, response below).
